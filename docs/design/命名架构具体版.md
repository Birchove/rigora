## 文献记录

```Python
class LiteratureRecord(BaseModel):
    # 文献基本信息
    title: str
    authors: list[str] = Field(default_factory=list)
    year: Optional[int] = None

    source_type: Literal[
        "paper",
        "book",
        "website",
        "dataset",
        "other"
    ]
    url: Optional[str] = None
    doi: Optional[str] = None
    # 原始摘要，如果检索系统能够获取
    abstract: Optional[str] = None
    # Agent 对该文献核心内容的简要概括
    summary: str
    # 该文献为什么和当前 Idea 有关
    relevance: str
    # 对当前科研问题有价值的关键结论
    key_findings: list[str] = Field(default_factory=list)
```

这里和 `EvidenceRef` 的区别非常重要：

```Plain Text
LiteratureRecord
    = 我搜到了什么、这篇东西讲什么

EvidenceRef
    = 我在当前判断中实际用了什么来支撑观点
```

```Python
def route_idea_review(
    result: IdeaReviewOutput,
):
    if (
        result.idea_type == "range"
        and result.action != "request_refinement"
    ):
        raise ValueError(
            "range 类型只能路由到 request_refinement"
        )

    match result.action:
        case "proceed_to_plan":
            return plan_loop_agent

        case "proceed_to_working":
            return working_qa_agent

        case "request_refinement":
            return initial_input_panel

        case "reject":
            return end_or_restart
```

```Python
class UserPlanFeedback(BaseModel):
    user_reason: str


DEFAULT_PLANNING_GUIDELINES = [
    "ResearchPlan 必须直接服务于 normalized_idea，不得擅自改变用户已经确认的核心研究目标。",
    "research_question 必须聚焦、可验证，并能够在用户的时间、资源和知识条件下执行。",
    "knowledge_requirements 只保留完成当前研究真正需要的内容；每项必须说明学习原因，外部事实应附有效 EvidenceRef。",
    "milestones 应按合理依赖顺序排列，每项具有明确目标和现实的 estimated_duration。",
    "KeyInsight 必须说明具体增量、成立理由及可验证路径，不得只更换术语、堆叠模块或使用空泛创新表述。",
    "时间、资源或证据不足时，将未确定事项写入 open_issues，不得用假设填补缺失信息。",
    "收到 previous_insight_check 时，只处理 revision_request 指向的问题，同时保持方案其余部分稳定。",
    "收到 user_feedback 时，判断其合理性后再修改方案，不得无条件接受或机械拒绝。",
    "每轮只做解决当前反馈所需的最小修改，并通过 change_summary 记录相对上一版的实际变化。",
]


DEFAULT_INTERACTION_GUIDELINES = [
    "首次生成方案时，response_to_user 应概括研究问题、实施路径、KeyInsight 和仍待确认事项。",
    "user_feedback 不为空时，必须直接回应 user_reason，并说明接受、部分接受或不接受的具体理由。",
    "接受用户意见时，在 change_summary 中记录对应修改；未修改的内容不得写入 change_summary。",
    "部分接受或不接受用户意见时，在 response_to_user 中给出与研究目标、证据或现实约束相关的理由。",
    "保持严格、专业、建设性；不得为了维持导师人设刻意制造分歧。",
    "不得声称方案已经得到用户确认；最终 accept、request_revision 或 override 由 Harness 的 UserPlanDecision gate 处理。",
]


class PlanLoopSysInput(SysInput):
    planning_guidelines: list[str] = Field(
        default_factory=lambda: (
            DEFAULT_PLANNING_GUIDELINES.copy()
        )
    )
    interaction_guidelines: list[str] = Field(
        default_factory=lambda: (
            DEFAULT_INTERACTION_GUIDELINES.copy()
        )
    )


class PlanLoopInput(BaseModel):
    idea: InitialInput
    sys_input: PlanLoopSysInput
    # 下方output包含ideareview的所有输出，规范化idea也在其中
    review_result: IdeaReviewOutput

    loop_round: int = 5

    # 上一次 key_insight_check_agent 的检查结果
    previous_insight_check: Optional["KeyInsightCheckOutput"] = None

    # 上一版方案
    previous_plan: Optional["ResearchPlan"] = None

    # 用户对上一版方案的反馈
    user_feedback: Optional[UserPlanFeedback] = None
```

```Plain Text
planning_guidelines
```

控制：

- 科研方案应该包含什么；

- 如何进行问题聚焦；

- 时间规划原则；

- 学习内容如何选择。

而：

```Plain Text
interaction_guidelines
```

控制你们“傲娇导师”的协商行为，例如：

- 不要无条件接受用户意见；

- 修改方案需要说明理由；

- 用户意见合理时应接受；

- 有分歧时明确表达导师立场；

- `user_feedback` 不为空时，必须明确回应用户提出的理由；

- 接受用户意见时，在 `change_summary` 中记录具体修改；

- 部分接受或不接受用户意见时，在 `response_to_user` 中说明具体原因，不得只用导师身份、主观偏好或人设拒绝。

此外，这里非常关键：

第一次：

```Python
previous_plan = None
user_feedback = None
```

内部 check 未通过时：

```Plain Text
previous_plan
+
previous_insight_check
```

一起输入，`user_feedback = None`，继续当前内部检查循环。

check 已通过但用户选择 `request_revision` 时：

```Plain Text
previous_plan
+
user_feedback: UserPlanFeedback
```

一起输入，并将 `previous_insight_check = None`，开启新的内部检查循环。用户反馈不计入上一轮最多 5 次的内部 check 轮次。

## Harness 最终裁决

```Python
class KeyInsightCheckOutput(BaseModel):
    """由 Harness 根据 Agent 评价确定性生成。"""

    assessment: KeyInsightAssessment

    final_score: float

    check_decision: bool

    decision_reason: str

        default_factory=list

    scoring_rule_version: str
```

## Harness 计算示例

```Python
SCORE_WEIGHTS = {
    "research_fit": 0.20,
    "novelty": 0.25,
    "research_value": 0.20,
    "testability_feasibility": 0.20,
    "evidence_support": 0.15,
}

PASS_SCORE = 6.0


def finalize_key_insight_check(
    assessment: KeyInsightAssessment,
) -> KeyInsightCheckOutput:
    raw_scores = {
        name: getattr(
            assessment.scores,
            name,
        ).score
        for name in SCORE_WEIGHTS
    }

    final_score = round(
        sum(
            raw_scores[name] * weight
            for name, weight
            in SCORE_WEIGHTS.items()
        ),
        1,
    )

    check_decision = final_score >= PASS_SCORE

    if check_decision:
        revision_request = []
        decision_reason = "加权总分达到通过阈值。"
    else:
        revision_request = (
            assessment.revision_suggestions[:3]
        )
        decision_reason = "加权总分未达到通过阈值。"

    return KeyInsightCheckOutput(
        assessment=assessment,
        final_score=final_score,
        check_decision=check_decision,
        decision_reason=decision_reason,
        revision_request=revision_request,
        scoring_rule_version="v1",
    )
```

# 五、用户对最终方案的决定

这个其实**不是 Agent**。

我建议单独做一个状态对象：

## UserPlanDecision

```Python
class UserPlanDecision(BaseModel):

    decision: Literal[
        "accept",
        "override",
        "request_revision"
    ]

    user_reason: Optional[str] = None

    # 如果 override，用户最终坚持的方案
    overridden_key_insight: Optional[KeyInsight] = None
```



Harness 在 `key_insight_check_agent` 通过后向用户展示最终方案并等待该状态对象：

```Plain Text
accept
    → 进入 WORKING

request_revision
    → user_reason 必填
    → 构造 UserPlanFeedback
    → 回填 plan_loop_agent
    → 重新开始内部 check 循环

override
    → 记录 OverrideRecord
    → 使用用户坚持的方案进入 WORKING
```

`check_decision = true` 只表示方案达到机器质量门槛，不表示方案已经得到用户确认。



如果：

```Python
decision == "override"
```

永久记录：

```Python
class OverrideRecord(BaseModel):
    agent_recommendation: KeyInsight

    user_choice: KeyInsight

    agent_reason: str

    user_reason: Optional[str] = None

    timestamp: str
```

这一块我认为将来是你们 Memory 中非常重要的数据。

例如：

```Plain Text
AI：
不建议使用 Method B。

用户：
坚持使用 Method B。

→ override = true
```

半年后系统仍然应该知道：

# 六、`working_qa_agent`

职责：

> 围绕 Harness 指定的单个当前实验任务，回答研究实施问题、请求必要澄清、维护实验事实，并判断当前实验任务是否完成。
>
>

`working_qa_agent` 不负责：

- 决定整个科研项目是否完成；

- 决定补充实验是否已经全部完成；

- 创建或修改 ValidationTask；

- 修改任务身份、来源或生命周期状态；

- 重新设计 ResearchPlan 或 KeyInsight；

- 生成论文结构或论文正文。

当前只定义四种顶层 Routing：

```Plain Text
answer
clarify
decline
success
```

具体问题类别和 Routing Policy 可以继续调整，不需要为每类问题增加新的 Schema。

# Input

## ExperimentInfo

`ExperimentInfo` 表示当前实验任务已经确认的最新事实快照。

一个 `ExperimentTaskContext` 只包含一个 `ExperimentInfo`。不同实验使用不同的 `ExperimentTaskContext`，不使用 `list[ExperimentInfo]` 表示多个实验。

```Python
class ExperimentInfo(BaseModel):
    current_experiment: Optional[str] = None

    expected_result: Optional[str] = None

    actual_result: Optional[str] = None

    observations: list[str] = Field(default_factory=list)
```

例如：

```Plain Text
{
  "current_experiment": "模型消融前的主实验",
  "expected_result": "F1 > 0.80",
  "actual_result": "F1 = 0.71",
  "observations": [
    "训练集指标正常",
    "验证集指标下降明显"
  ]
}
```

这里的 `ExperimentInfo` 是当前权威状态，不是历史版本列表。

历史变更应由持久化层单独保存，不放入 Agent3 的当前任务上下文。

## ExperimentTaskContext

`ExperimentTaskContext` 表示 Agent3 当前正在处理的唯一实验任务。

```Python
from typing import Self
from pydantic import model_validator


ExperimentTaskKind = Literal[
    "main",
    "validation",
]


ExperimentTaskOrigin = Literal[
    "plan",
    "forward",
    "validation_plan",
]


ExperimentTaskStatus = Literal[
    "pending",
    "in_progress",
    "completed",
    "blocked",
    "cancelled",
]
```

```Python
class ExperimentTaskContext(BaseModel):
    # Harness 生成的稳定任务标识
    task_id: str

    # 主实验或补充实验
    task_kind: ExperimentTaskKind

    # 任务是通过什么入口创建的
    origin: ExperimentTaskOrigin

    # 任务调度生命周期
    # 只能由 Harness 修改
    status: ExperimentTaskStatus

    # 补充实验所属的主实验
    # main 时必须为空
    # validation 时必须存在
    parent_task_id: Optional[str] = None

    # task_kind = validation 时必须存在
    # task_kind = main 时必须为空
    validation_task: Optional[
        "ValidationTask"
    ] = None

    # 当前任务已经积累的实验事实
    experiment_info: ExperimentInfo = Field(
        default_factory=ExperimentInfo
    )

    @model_validator(mode="after")
    def validate_task_shape(self) -> Self:
        if self.task_kind == "main":
            if self.parent_task_id is not None:
                raise ValueError(
                    "main task 不能包含 "
                    "parent_task_id"
                )

            if self.validation_task is not None:
                raise ValueError(
                    "main task 不能包含 "
                    "validation_task"
                )

        if self.task_kind == "validation":
            if self.parent_task_id is None:
                raise ValueError(
                    "validation task 必须包含 "
                    "parent_task_id"
                )

            if self.validation_task is None:
                raise ValueError(
                    "validation task 必须包含 "
                    "validation_task"
                )

        return self
```

字段语义：

```Plain Text
task_kind = main
    表示当前处理主实验

task_kind = validation
    表示当前处理一项补充实验
```

```Plain Text
origin = plan
    用户接受 ResearchPlan 后，
    Harness 创建主实验任务

origin = forward
    用户已有实验基础，
    从 idea_review_agent 进入 Working

origin = validation_plan
    用户从补充实验候选中选择任务后，
    Harness 创建补充实验任务
```

Harness 应根据稳定的业务语义 `task_kind` 和 `origin` 路由。

`status` 表示任务生命周期，不表示实验结论是否支持假设：

```Plain Text
status = completed
    只表示实验任务已经完成

status = completed
    不等于实验支持预期结论
```

可能存在：

```Plain Text
status = completed
actual_result 不支持 expected_result
```

这仍然是一个有效完成的实验。

## WorkingQAInput

# Output

现在只定义最上层 Routing，不定义详细边界。

```Python
class WorkingQAOutput(BaseModel):
    action: Literal[
        "answer",
        "clarify",
        "decline",
        "success",
    ]
    # 选择当前 action 的原因
    reason: str
    # 面向用户的回复
    # success 时必须为空字符串
    reply: str
    # 当前实验信息的完整新快照
    # 不是局部 patch
    updated_experiment_info: Optional[
        ExperimentInfo
    ] = None
    # 实际支撑本轮回答的证据
    evidence: list[EvidenceRef] = Field(
        default_factory=list
    )
    @model_validator(mode="after")
    def validate_action_fields(self) -> Self:
        if self.action == "success":
            if self.reply != "":
                raise ValueError("success 时 reply 必须为空字符串")

            if self.updated_experiment_info is None:
                raise ValueError("success 时必须返回完整的updated_experiment_info")

            actual_result = (self.updated_experiment_info.actual_result)

            if (actual_result is None or not actual_result.strip()):
                raise ValueError( "success 时 actual_result不能为空")
        else:
            if not self.reply.strip():
                raise ValueError("非 success 状态必须提供 reply")
        return self
```

## Harness 处理规则

Agent3 输出后，Harness 按以下方式处理。

### answer / clarify / decline

```Plain Text
校验 WorkingQAOutput
→ 合并或写入 updated_experiment_info
→ task_context.status 保持 in_progress
→ 等待用户下一次输入
```

其中 decline 只表示当前问题被拒绝，不表示当前实验任务失败或取消。

### success

```Plain Text
校验 WorkingQAOutput
→ 写入最终 ExperimentInfo
→ 将 task_context.status 设置为 completed
→ 根据 task_context.task_kind 路由
```

主实验：

```Plain Text
task_kind = main
→ 生成主实验完成结果
→ 调用 complete_agent
```

补充实验：

```Plain Text
task_kind = validation
→ 生成 ValidationResult
→ 调用 complete_agent
```

Agent3 不直接调用 Agent2 或 Complete Agent。它只输出结构化结果，由 Harness 根据 `task_kind` 和状态路由。
